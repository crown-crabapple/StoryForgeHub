# Contributing to StoryForge

Thank you for helping. StoryForge is licensed under `AGPL-3.0-only`; by sending a change you agree that it is released under the same licence. Please read the [code of conduct](CODE_OF_CONDUCT.md). To report a security problem, use [SECURITY.md](SECURITY.md), not a public issue.

## Set up

Node 24 (see `.nvmrc`; `>=22` works) and npm. Then `npm ci` and `npm run build`. [docs/development.md](docs/development.md) has the two development loops, the test commands, the workspace map and the layer rules.

Before you send anything, run the one command that is the CI:

```sh
npm run ci
```

It checks the lockfile, builds, lints, runs every test and the large-library tests, runs a UI smoke test, runs the security and licence checks and builds the release zip. It never needs Docker. The `npm audit` step needs the network and skips itself with a notice when offline. `.github/workflows/ci.yml` runs the same command on Linux, macOS and Windows.

## The job and contract workflow

Work is planned as jobs (`M<milestone>-J<number>`), and each job has a contract in `docs/contracts/` that says what must be true when it is done. If your change is more than a small fix:

1. Write or update a contract in `docs/contracts/` first: the behaviour, the boundaries, and how it will be proved.
2. Build to the contract; do not widen it while you are in there. If the contract is wrong, change the contract in its own commit and say why.
3. Prove it with tests that fail without your change.
4. Record what you did not do (known limits) so release notes can say it in plain words.

A small bug fix needs no contract, only a test.

## Tests are required

- A bug fix comes with a regression test that fails before the fix.
- A new behaviour comes with tests for its normal use, its refusals and its edge cases.
- Tests start real servers on `127.0.0.1` with port `0` in temporary folders and never need the internet, Docker or a browser.
- Run a single file with the config isolation, so a test never touches your real settings: `node --import ./scripts/test-isolate-config.mjs --test <file>`.
- Slow large-library tests are named `*.large.mjs` and run with `npm run test:large`.

## The boundaries

ESLint and tests enforce these. A change that crosses one will not pass `npm run ci`.

- **Single writer.** `packages/store` is the only code that writes project files (atomic, journaled, with conflict detection). Everything else asks the store. Reads are confined to a few named modules; see `eslint.config.mjs`.
- **Network module.** Outbound network code exists in exactly two files: `packages/ai/src/transport.mjs` (the optional AI provider) and `packages/integrations/src/webhook-transport.mjs` (webhooks the author set up). `fetch`, `node:https`, `node:net` and the rest are lint errors everywhere else.
- **No telemetry.** No analytics, no update check, no crash reporting, no "phone home" of any kind, not even optional. A change that adds one will be declined.
- **Layers.** `apps/web` talks to the server over `/api` only; `apps/server` uses the `FileRepository` interface; `packages/core` is the only place that reads project files.
- **Markdown is canonical.** Anything stored in `.storyforge/` is disposable and must be rebuildable from the Markdown files.
- **Security cores** (password hashing, sessions, the route policy, plugin policy, the key store) change only with a maintainer's review and tests that attack the change.

## Commit style

- One logical change per commit. The subject says what changed, in the present tense, in plain words (for example `Export: keep chapter order when two scenes share a number`). The body says why, if it is not obvious.
- Keep generated files, local settings and anything that came from a real manuscript out of commits.
- Do not rewrite history that others have pulled.

## How to add a fixture

Fixtures are small, synthetic book folders (never real manuscript text) under `packages/format/fixtures/`.

1. Valid books go in `fixtures/valid/<name>/`, invalid ones in `fixtures/invalid/<name>/`. Use the invented "Salt Orchard" style of content.
2. Add an `expected.json` next to it listing the diagnostics the validator must report (an empty list for a valid book). The golden tests in `packages/format/test/` read it.
3. If the fixture is built by a script, add the script to `packages/format/test/` (see `build-fixtures.mjs`) so it can be regenerated byte for byte.
4. Fixtures are matched byte for byte: `.gitattributes` keeps them out of line-ending conversion. Do not let an editor reformat them.
5. Run `npm test -w @storyforge/format` and then `npm run ci`.

## Releases

Maintainers follow [docs/release-checklist.md](docs/release-checklist.md). Versions are set in step in every package with `node scripts/version.mjs <x.y.z>`; the policy is in [docs/compatibility.md](docs/compatibility.md).
