# StoryForge 0.1.0 release notes

The first release of StoryForge, a Markdown-first novel studio you run on your own computer, or on a server for a group. Licence: `AGPL-3.0-only`. What is in it, by feature family, is in the [changelog](../../CHANGELOG.md); how to install it is in [install.md](../install.md).

## Guarantees

These hold for every release:

- no paywalls;
- no mandatory telemetry (none at all);
- no account required in personal mode;
- Markdown is canonical and the folder is the whole project;
- AI is off until configured, and nothing is sent without preview and Send;
- receipts are private.

## Known limitations

Collected from the result and gate reports of milestones M05 to M08 and stated in plain words. Nothing here loses your writing; each is a limit to know about.

### Writing, the editor and the phone

- On a phone the editor toolbar still wraps to three rows.
- The page title stays "StoryForge" and does not name the book or the view.
- Chat replies from the AI workshop do not show bold or italic text.
- Some earlier interface rough edges remain: Codex blurbs can show raw slugs, search snippets can show raw Markdown, and the editor script is large (about 800 kB).
- The dialog focus trap and the focus after Undo were checked by hand for the Export dialog; there is no automated browser test for them.
- The offline save queue is tested against a stand-in for the browser database, not a real browser. Trying it in a real browser (developer tools set to offline) and a screen-reader pass with NVDA are checks for the owner.

### Speed

- Several read routes (continuity, suggestions, the Codex, the timeline, notes) check the whole book on every request. On a 130,000-word book one scene or entry request takes about 0.7 s and a continuity check 1.6 to 1.9 s. Small and normal books are fast: opening a scene is about 1 to 2 ms and a full index rebuild of a very large synthetic book is 3.4 s.
- Restoring a backup on Windows varies widely in time (1.6 to 16 s for a medium book), probably because of antivirus scanning.
- One export command-line test and one large test are sensitive to timing and can fail when the computer is heavily loaded; they pass on their own.

### Continuity, the index and series

- Running a series book on its own can show a false `W311` warning for labels its series defines. Two series with the same slug are not checked.
- Index entries for other books of a series can go stale until a rebuild. The file watcher does not watch a series' `codex/` folder, so edits made outside the app to shared files are picked up only on the next app write or `rebuild`.
- Project-level `preferences:` in `library.md` and `book.md` are edited by hand; there is no form. Prompt components are hand-written files.
- `rebuild` and `repair --apply` take the library lock, so they refuse (exit 3) while the app is running on the same library. Stop StoryForge first.

### Export

- A Word file has never been opened in Microsoft Word on the build machine. PDF export uses the standard fonts, so non-Latin text shows as `?`.
- The back up and restore buttons in the app were not walked again in the last milestone; they are covered by earlier tests and walks.

### Receipts

- A hard kill of the app (power loss, killing the process) loses the record of writes that were not yet flushed; they then show as outside changes.
- Entry, thread and note body saves are not yet tracked as the app's own writes.

### The Claude-Book adapter

- The style checker's own report files pile up in the adapter's `.work/` folder.
- Very short chapters fail the style checker's dialogue minimum.

### Importing from the old StoryForgeHub

- Scene links to unknown names are kept as written, so the imported book shows `E301` errors for them (the report lists them as `unknown-link`).
- Chapter references (the ledger and events) resolve to the chapter's first scene; a prologue becomes chapter 1.
- Series names are kept on the book as text; series folders are not created.
- Two ledger items point at chapters with no scenes; they are kept in the thread text for you to fix.
- Aggregated tables (state events, knowledge facts, canvas, captures, dictionary, continuity exemptions) are checked by count, not row by row.
- The guard against importing into a `legacy-StoryForgeHub` folder works by folder name only.
- Only the SQLite path of the dump tool was tested end to end; the MySQL path is untested until you run it. The dump steps in [migration.md](../migration.md) have not been run on a clean machine.

### Shared mode and accounts

- There is no in-app password change for the owner. Rotate it with `shared reset-owner`; for a member, remove and invite again.
- Viewers and reviewers can read the AI status (the active profile name, model and address). Share links cannot.
- Several editing controls in the right rail are not hidden for reviewers and viewers; the server refuses them (403).
- In personal mode, every page load logs a 404 for `/api/auth/me` in the browser console. This is intended: personal mode has no sign-in routes.
- A flood of anonymous refused writes, or of requests with an unknown token, makes the audit log grow. The login rate limits do not cover this.
- The audit head sits in the same folder as the log. It detects accidental or simple tampering; someone who can write to that folder can rewrite both.
- Behind a reverse proxy the per-address login limit counts the proxy as one client. The per-username limit still applies.
- Login, the read-only editor for reviewers and viewers, and the stale-save panel were not walked in a real browser in shared mode; they are covered by render tests and tests against a real server.

### Plugins and webhooks

- Webhook events fire only for writes made through the HTTP server, not the command line.
- A webhook disabled after 20 failures must be created again.
- A plugin webhook needs a public `https` address; a plugin cannot point one at the computer StoryForge runs on.

### Docker and self-hosting

- The Docker files were checked by tests but the live `docker compose up` run has not been done (Docker was not installed on the build machine). The steps are in [self-hosting.md](../self-hosting.md) and the [release checklist](../release-checklist.md).
- The base image is pinned by tag, not by digest.
- Folders mounted into the container must be owned by uid 10001 on Linux.

### The release itself

- The release zip does not keep the executable bit on `storyforge.sh`: start it with `sh storyforge.sh`, or run `chmod +x storyforge.sh` once.
- The continuous-integration workflow was written and checked as YAML but has never run, because the project has no remote repository yet. `npm run ci` is the same set of steps and is what was run.
- The contact addresses in `SECURITY.md` and `CODE_OF_CONDUCT.md` are placeholders (`<ADD CONTACT>`) until the owner fills them in.

## Upgrade notes

### From the old StoryForgeHub

Follow [migration.md](../migration.md): take a dump of the legacy database with the read-only dump tool, run a dry run, import into a new folder, reconcile, and compare a second import. The legacy data is never changed. Keep your legacy copy until you have checked the result.

### Between StoryForge versions

- Replace the program, keep your library: your books are plain Markdown folders and are not touched by an upgrade.
- Indexes rebuild: when a release changes the index layout, the old index is thrown away and rebuilt from your Markdown files the first time the book is opened, or with `rebuild`. Nothing you wrote lives only in the index.
- Shared mode and Docker: see the Upgrade sections of [install.md](../install.md) and [self-hosting.md](../self-hosting.md). Stop the old version, start the new one on the same folders.
- The rules that keep files, the API, plugin manifests and shared-data files compatible are in [compatibility.md](../compatibility.md).
